# План нагрузочного тестирования модуля диалогов

## Цель
Сравнить производительность модуля диалогов до и после переноса хранения и логики в In-Memory СУБД (Redis).

## Область теста
- `POST /api/v1/dialog/{user_id}/send` - отправка сообщения.
- `GET /api/v1/dialog/{user_id}/list` - чтение диалога между двумя пользователями.

## Тестовый сценарий
1. В `setup` создаются тестовые пользователи через API.
2. Для каждого пользователя выполняется логин и получение access token.
3. Пользователи объединяются в пары, диалоги прогреваются начальными сообщениями.
4. Во время теста запускаются 2 параллельных потока:
   - write-heavy поток (`send`) - отправка сообщений;
   - read поток (`list`) - чтение истории диалога.

## Нагрузочный профиль
- Разогрев 2 минуты.
- Плато 8 минут.
- Плавный спад 1 минута.
- Тип нагрузки: `ramping-arrival-rate`.

## Метрики и пороги
- Основные:
  - `dialog_send_latency` (`p95 < 400ms`, `p99 < 800ms`);
  - `dialog_list_latency` (`p95 < 600ms`, `p99 < 1000ms`);
  - `http_req_failed < 1%`;
  - `dialog_send_errors < 2%`;
  - `dialog_list_errors < 2%`.
- Дополнительно:
  - throughput по операциям `dialog_send_rpc` и `dialog_list_rpc`;
  - утилизация CPU/RAM контейнеров приложения и БД.

## Процедура сравнения ДО/ПОСЛЕ
1. Запустить тест на текущей реализации (SQL):
   - `make run_load_dialog_test_single_db`
2. Сохранить отчеты и ключевые метрики в файл сравнения.
3. Внести изменения с Redis + UDF/Lua.
4. Повторить тест с тем же профилем и длительностью.
5. Сравнить:
   - latency (`p95/p99`);
   - error rate;
   - throughput;
   - потребление ресурсов.

## Критерий успешности
- Латентность и/или пропускная способность улучшаются или не деградируют сверх допустимых порогов.
- Ошибки находятся в пределах заданных threshold.
- Есть зафиксированное сравнение результатов "до/после".
